# Deployment Architecture - Departamento Node

## Overview

The **Departamento** (Department) node implements the second level of the Map-Reduce architecture in the distributed voting system. It serves as an intermediate consolidation layer between voting locations (`lugar-votacion`) and the central server (`servidor-central`), aggregating vote deltas from multiple locations within a department before forwarding consolidated results.

## Component Architecture

### Core Components

#### 1. DepartamentoVotacionApp (Main Application)
- **Type**: Main class / Entry point
- **Runtime**: Java application with Ice middleware
- **Responsibility**: Application lifecycle management
- **Configuration**: External properties file (`departamento.properties`)
- **Initialization Sequence**:
  1. Load configuration from external file
  2. Initialize Ice communicator
  3. Create department controller with Map-Reduce capabilities
  4. Start Ice server for receiving deltas
  5. Register `ReceptorVotos` servant
  6. Verify connectivity to central server
  7. Enter service loop

#### 2. DepartamentoController (Business Logic Controller)
- **Type**: Business logic controller with Map-Reduce Level 2
- **Threading**: Configurable thread pool for parallel processing
- **Components**:
  - `ServicioComunicacionDepartamento`: Outbound communication to central server
  - `ServicioVerificacionConectividad`: Connection health monitoring
  - `RepositorioDeltas`: Thread-safe delta storage (ConcurrentHashMap)
  - `GeneradorDeltas`: Delta consolidation with threshold management
  - `ExecutorService`: Thread pool for MAP PHASE processing

#### 3. ServidorIceDepartamento (Ice Server/Servant)
- **Type**: Ice servant implementing `ReceptorVotos` interface
- **Protocol**: Ice over TCP
- **Services Exposed**:
  - `recibirDeltaConteo(DeltaConteo delta)`: Receives vote deltas from locations
  - `ping()`: Health check endpoint
  - `recibirValidacionVotante()`: Not implemented (throws UnsupportedOperationException)

## Map-Reduce Architecture (Level 2)

### MAP PHASE (Parallel Processing)
```
Lugar Votación Delta → Thread Pool → Parallel Consolidation
                      ↓
               RepositorioDeltas (ConcurrentHashMap)
                      ↓
              Threshold-based aggregation
```

### REDUCE PHASE (Consolidation & Forwarding)
```
Consolidated Department Delta → ServicioComunicacionDepartamento → Servidor Central
```

### Threshold Management
- **Vote Threshold**: `delta.umbral.votos` (default: 2000 votes)
- **Time Threshold**: `delta.umbral.tiempo` (default: 3000ms)
- **Auto-forwarding**: When either threshold is reached


```properties

conexion.timeout=3000
```

## Network Interfaces

### Inbound Interfaces

#### 1. Delta Reception Interface
- **Protocol**: Ice over TCP
- **Port**: Configurable via `departamento.puerto` (default: 7001)
- **Service**: `ReceptorVotos`
- **Identity**: `"ReceptorVotos"`
- **Methods**:
  - `recibirDeltaConteo(DeltaConteo delta)`: Main delta reception
  - `ping()`: Health check

### Outbound Interfaces

#### 1. Central Server Interface
- **Protocol**: Ice over TCP
- **Target**: `servidor-central`
- **Port**: Configurable via `servidor.central.puerto` (default: 6000)
- **Service**: `ReceptorVotos`
- **Purpose**: Forward consolidated department deltas

## Data Flow

### Delta Processing Flow
```
1. Lugar Votación → [Ice/TCP:7001] → ServidorIceDepartamento
2. ServidorIceDepartamento → DepartamentoController.procesarDelta()
3. Thread Pool (MAP PHASE) → GeneradorDeltas.procesarDelta()
4. RepositorioDeltas.consolidar() → Thread-safe aggregation
5. Threshold Check → If met: GeneradorDeltas.enviarDelta()
6. ServicioComunicacionDepartamento → [Ice/TCP:6000] → Servidor Central
```

### Map-Reduce State Management
- **Shared State**: `ConcurrentHashMap<Integer, Integer>` (candidate_id → vote_count)
- **Thread Safety**: All operations on shared state are atomic
- **Consolidation**: Periodic or threshold-based delta generation

## Runtime Dependencies

### Java Runtime
- **Version**: Java 8+ required
- **Memory**: Configurable JVM heap (depends on department size)
- **Threading**: Multiple threads for Map-Reduce processing

### Ice Middleware
- **Version**: ZeroC Ice 3.7+
- **Components**: Ice runtime, Ice for Java bindings
- **Services**: Object adapter, proxy management, serialization

### Network Dependencies
- **Inbound**: Port accessibility for lugar-votacion connections
- **Outbound**: Network connectivity to servidor-central
- **DNS**: Hostname resolution for configured endpoints

## Service Management

### Startup Sequence
1. Load `departamento.properties` from JAR directory
2. Initialize Ice communicator and thread pool
3. Create and configure object adapter
4. Register `ReceptorVotos` servant
5. Activate adapter and start listening
6. Verify connectivity to central server
7. Enter service loop (waitForShutdown)

### Shutdown Sequence
1. Signal handler triggers graceful shutdown
2. Send final consolidated delta (if any)
3. Shutdown thread pool with 5-second timeout
4. Close all Ice connections
5. Destroy Ice communicator
6. Exit application

### Health Monitoring
- **Ice ping()**: Built-in health check endpoint
- **Connectivity verification**: Periodic checks to central server
- **Thread pool monitoring**: Automatic resource management

## Error Handling & Resilience

### Connection Failures
- **Retry logic**: Configurable retry attempts for central server
- **Timeout handling**: Configurable timeouts for all operations
- **Graceful degradation**: Continue accepting deltas even if forwarding fails

### Processing Failures
- **Thread isolation**: Individual thread failures don't affect others
- **Delta buffering**: Temporary storage until successful forwarding
- **Resource cleanup**: Automatic cleanup of failed operations

### Data Consistency
- **Atomic operations**: All shared state modifications are atomic
- **Final delta**: Ensures no data loss during shutdown
- **Thread-safe consolidation**: ConcurrentHashMap ensures consistency

## Performance Characteristics

### Throughput
- **Parallel processing**: Configurable thread pool size
- **Batch processing**: Delta consolidation reduces network traffic
- **Threshold-based forwarding**: Balances latency vs. efficiency

### Scalability
- **Horizontal**: Multiple departments can run independently
- **Vertical**: Thread pool size can be tuned for hardware
- **Network**: Efficient delta consolidation reduces bandwidth

### Resource Usage
- **Memory**: Proportional to active vote deltas and thread pool
- **CPU**: Multi-threaded processing utilizes available cores
- **Network**: Optimized through delta consolidation

## Security Considerations

### Network Security
- **Internal network**: Designed for trusted internal deployment
- **No authentication**: Relies on network-level security
- **No encryption**: Plain TCP (consider VPN for production)

### Data Integrity
- **Structured data**: Ice serialization ensures data integrity
- **Atomic operations**: Thread-safe vote counting
- **Error boundaries**: Isolated processing prevents corruption

## Monitoring & Diagnostics

### Available Endpoints
- **Health check**: `ping()` method via Ice
- **Connectivity test**: Built-in verification to central server

### Logging
- **Startup logs**: Configuration and connectivity status
- **Error logs**: Connection failures and processing errors
- **Shutdown logs**: Graceful shutdown confirmation

### Operational Metrics
- **Delta processing rate**: Monitored through thread pool
- **Consolidation efficiency**: Vote and time thresholds
- **Network health**: Connection success/failure rates

## Integration Points

### Upstream Systems (Data Sources)
- **Lugar Votación**: Multiple voting location nodes
- **Protocol**: Ice over TCP
- **Data Format**: `DeltaConteo` structured deltas

### Downstream Systems (Data Destinations)
- **Servidor Central**: Single central consolidation server
- **Protocol**: Ice over TCP
- **Data Format**: Consolidated `DeltaConteo` deltas

### Configuration Management
- **External files**: Properties loaded from JAR directory
- **Runtime configuration**: No dynamic reconfiguration
- **Deployment consistency**: Same configuration format across environments

This deployment architecture ensures the departamento node efficiently consolidates vote deltas from multiple locations while maintaining high throughput, reliability, and data consistency in the distributed voting system.
