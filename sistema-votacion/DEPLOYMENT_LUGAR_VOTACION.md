# Deployment Architecture - Lugar Votación Node

## Overview

The **Lugar Votación** (Voting Location) node implements the first level of the Map-Reduce architecture in the distributed voting system. It serves as an intermediate consolidation layer between multiple voting stations (`mesa-votacion`) and department-level nodes (`departamento`), aggregating vote deltas from voting stations within a geographic location before forwarding consolidated results to the next tier.

## Component Architecture

### Core Components

#### 1. LugarVotacionApp (Main Application)
- **Type**: Main class / Entry point
- **Runtime**: Java application with Ice middleware
- **Responsibility**: Application lifecycle management and service orchestration
- **Configuration**: External properties file (`lugar-votacion.properties`)
- **Initialization Sequence**:
  1. Load configuration from external file or embedded resources
  2. Initialize Ice communicator
  3. Create voting location controller with Map-Reduce Level 1 capabilities
  4. Start Ice server for receiving deltas from brokers/mesas
  5. Register `ReceptorVotos` servant
  6. Verify connectivity to destination broker
  7. Enter service loop

#### 2. LugarController (Business Logic Controller)
- **Type**: Business logic controller with Map-Reduce Level 1
- **Threading**: Configurable thread pool for parallel processing
- **Components**:
  - `ServicioComunicacionLugar`: Outbound communication to destination broker
  - `ServicioVerificacionConectividad`: Connection health monitoring
  - `RepositorioDeltas`: Thread-safe delta storage (ConcurrentHashMap)
  - `GeneradorDeltas`: Delta consolidation with threshold management
  - `ExecutorService`: Thread pool for MAP PHASE processing

#### 3. ServidorIceLugar (Ice Server/Servant)
- **Type**: Ice servant implementing `ReceptorVotos` interface
- **Protocol**: Ice over TCP
- **Services Exposed**:
  - `recibirDeltaConteo(DeltaConteo delta)`: Receives vote deltas from voting stations
  - `recibirValidacionVotante(String documento, int candidatoId)`: Forwards voter validation requests
  - `ping()`: Health check endpoint

## Map-Reduce Architecture (Level 1)

### MAP PHASE (Parallel Processing)
```
Mesa Votación Delta → Thread Pool → Parallel Consolidation
                     ↓
               RepositorioDeltas (ConcurrentHashMap)
                     ↓
              Threshold-based aggregation
```

### REDUCE PHASE (Consolidation & Forwarding)
```
Consolidated Location Delta → ServicioComunicacionLugar → Destination Broker → Departamento
```

### Threshold Management
- **Vote Threshold**: `delta.umbral.votos` (default: 500 votes)
- **Time Threshold**: `delta.umbral.tiempo` (default: 1000ms)
- **Auto-forwarding**: When either threshold is reached

## Network Interfaces

### Inbound Interfaces

#### 1. Delta Reception Interface
- **Protocol**: Ice over TCP
- **Port**: Configurable via `lugar.puerto` (default: 8001)
- **Service**: `ReceptorVotos`
- **Identity**: `"ReceptorVotos"`
- **Methods**:
  - `recibirDeltaConteo(DeltaConteo delta)`: Main delta reception and processing
  - `recibirValidacionVotante(String documento, int candidatoId)`: Voter validation forwarding
  - `ping()`: Health check

### Outbound Interfaces

#### 1. Destination Broker Interface
- **Protocol**: Ice over TCP
- **Target**: lugar-departamento broker
- **Port**: Configurable via `broker.destino.puerto` (default: 9001)
- **Service**: `BrokerService`
- **Purpose**: Forward consolidated location deltas and validation requests

## Data Flow

### Delta Processing Flow
```
1. Mesa Votación → [Broker] → [Ice/TCP:8001] → ServidorIceLugar
2. ServidorIceLugar → LugarController.procesarDelta()
3. Thread Pool (MAP PHASE) → GeneradorDeltas.procesarDelta()
4. RepositorioDeltas.consolidar() → Thread-safe aggregation
5. Threshold Check → If met: GeneradorDeltas.enviarDelta()
6. ServicioComunicacionLugar → [Ice/TCP:9001] → Destination Broker
```

### Voter Validation Flow
```
1. Mesa Votación → [Broker] → [Ice/TCP:8001] → ServidorIceLugar
2. ServidorIceLugar.recibirValidacionVotante()
3. LugarController.validarVoto()
4. ServicioComunicacionLugar.reenviarValidacionVotante()
5. [Ice/TCP:9001] → Destination Broker → Validation Response
```

### Map-Reduce State Management
- **Shared State**: `ConcurrentHashMap<Integer, AtomicInteger>` (candidate_id → vote_count)
- **Thread Safety**: All operations on shared state are atomic
- **Consolidation**: Periodic or threshold-based delta generation

## Service Management

### Startup Sequence
1. Load `lugar-votacion.properties` (external or embedded)
2. Initialize Ice communicator and thread pool
3. Create and configure object adapter
4. Register `ReceptorVotos` servant
5. Activate adapter and start listening
6. Verify connectivity to destination broker
7. Initialize Map-Reduce components (repository, generator)
8. Enter service loop (waitForShutdown)

### Shutdown Sequence
1. Signal handler triggers graceful shutdown
2. Send final consolidated delta (if any)
3. Shutdown thread pool with 5-second timeout
4. Close all Ice connections
5. Destroy Ice communicator
6. Exit application

### Health Monitoring
- **Ice ping()**: Built-in health check endpoint
- **Broker connectivity**: Periodic verification of destination broker
- **Thread pool monitoring**: Automatic resource management

## Error Handling & Resilience

### Connection Failures
- **Retry logic**: Configurable retry attempts for destination broker
- **Timeout handling**: Configurable timeouts for all operations
- **Graceful degradation**: Continue accepting deltas even if forwarding fails

### Processing Failures
- **Thread isolation**: Individual thread failures don't affect others
- **Delta buffering**: Temporary storage until successful forwarding
- **Resource cleanup**: Automatic cleanup of failed operations

### Data Consistency
- **Atomic operations**: All shared state modifications are atomic
- **Final delta**: Ensures no data loss during shutdown
- **Thread-safe consolidation**: ConcurrentHashMap ensures consistency

## Performance Characteristics

### Throughput
- **Parallel processing**: Configurable thread pool size (default: 12 threads)
- **Batch processing**: Delta consolidation reduces network traffic
- **Threshold-based forwarding**: Balances latency vs. efficiency

### Scalability
- **Horizontal**: Multiple locations can run independently
- **Vertical**: Thread pool size can be tuned for hardware
- **Network**: Efficient delta consolidation reduces bandwidth

### Resource Usage
- **Memory**: Proportional to active vote deltas and thread pool
- **CPU**: Multi-threaded processing utilizes available cores
- **Network**: Optimized through delta consolidation

## Integration Points

- **Protocol**: Ice over TCP
- **Data Format**: `DeltaConteo` structured deltas

### Downstream Systems (Data Destinations)
- **Lugar-Departamento Broker**: Routing broker to department level
- **Protocol**: Ice over TCP via `BrokerService`
- **Data Format**: Consolidated `DeltaConteo` deltas

### Auxiliary Systems
- **Validation Services**: Voter validation forwarding through broker chain
- **Protocol**: Ice over TCP
- **Purpose**: Transparent voter validation pass-through

### Configuration Management
- **External files**: Properties loaded from JAR directory or embedded
- **Runtime configuration**: No dynamic reconfiguration
- **Deployment consistency**: Same configuration format across environments

## Architectural Patterns

### Map-Reduce Implementation
- **MAP PHASE**: Parallel processing of incoming deltas from multiple voting stations
- **Shared State**: Thread-safe consolidation using ConcurrentHashMap
- **REDUCE PHASE**: Threshold-based generation of consolidated deltas
- **State Reset**: Clean slate after each successful forwarding

### Event-Driven Processing
- **Asynchronous Processing**: Thread pool handles delta processing
- **Threshold Events**: Time and vote-based triggering
- **Callback Pattern**: Delta forwarding via functional interfaces

### Proxy Pattern
- **Transparent Forwarding**: Voter validation requests pass through unchanged
- **Service Virtualization**: Acts as intermediate layer in validation chain
- **Load Distribution**: Participates in system-wide load balancing

## Deployment Best Practices

### Resource Allocation
- **Thread Pool Sizing**: Size according to expected voting station count
- **Memory Configuration**: Adjust heap size based on peak voting periods
- **Network Buffers**: Optimize Ice connection parameters

### Monitoring Strategy
- **Health Checks**: Regular ping verification of destination connectivity
- **Performance Metrics**: Monitor consolidation rates and forwarding success
- **Error Tracking**: Log and alert on connection or processing failures

### Operational Procedures
- **Graceful Shutdown**: Always send final delta before termination
- **Configuration Validation**: Verify connectivity during startup
- **Resource Cleanup**: Ensure proper thread pool and connection cleanup

This deployment architecture ensures the lugar-votacion node efficiently consolidates vote deltas from multiple voting stations while maintaining high throughput, reliability, and data consistency in the distributed voting system's Map-Reduce hierarchy.
